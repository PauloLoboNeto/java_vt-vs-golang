Benchmark de I/O: Java, Go, Rust e Python esperando uma API lenta

Cada requisição recebida chama uma API externa que demora 5 s e devolve a resposta, sem trabalho de CPU no handler. Cada alvo roda sozinho em um container com 2 vCPU e 1 GB. A pergunta é quanto cada plataforma gasta em memória, CPU e latência para manter milhares de chamadas paradas ao mesmo tempo.

Esta página reúne as cinco rodadas completas: a trilha padrão (Java na JVM, Java em Native Image e Go), o Rust, a trilha otimizada, com o Java migrado de Tomcat para Jetty, a carga constante de 100 req/s e a trilha Python. Os valores são a mediana de 3 repetições, com 30 s de warm-up e 180 s medidos. O código e os dados brutos estão em PauloLoboNeto/java_vt-vs-golang.

Resumo

  • Na configuração padrão, só Go e Rust atenderam aos três níveis. Com 10.000 VUs, o Go fez 1.999,6 de 2.000 req/s com 407 MiB de pico e o Rust 1.999,4 com 629 MiB. Java na JVM (Tomcat) e em Native Image tiveram 100% de erros por falta de memória.
  • Otimizado, todo alvo Java atendeu a 10.000 VUs em 1 GB, sem erros. O que mais pesou foi trocar o Tomcat pelo Jetty e remover dois limites do Jetty: o pool de 200 tarefas e o cache de cabeçalhos de cerca de 100 KB por conexão. A JVM com G1 fez 1.992,5 req/s com 953 MiB de pico, ainda 2,8 vezes a memória e 5,4 vezes a CPU por requisição do Go otimizado.
  • No Native Image, o coletor decide. Com Serial (GraalVM CE), ficou em 1.650,3 req/s (82,5% do ideal) com 10.000 VUs. Com G1 (Oracle GraalVM), fez 1.996,0 req/s.
  • Com 100 req/s constantes, os 10 alvos atenderam sem erros e sem iterações descartadas. A diferença foi só custo: memória de pico de 24,8 MiB (Go otimizado) a 430,9 MiB (JVM padrão) e CPU de 0,161 a 1,576 CPU-s por 1.000 requisições.
  • Em Python, a pilha decide. Só o aiohttp puro acompanhou o Go com 10.000 VUs, com 3,2 vezes a CPU por requisição. FastAPI + httpx teve 100% de erros desde 5.000 VUs, por um custo quadrático no pool de conexões do httpcore.
  • Startup: Go, Rust e Native ficam prontos em 120 a 164 ms. A JVM leva 2.319 ms, ou 1.156 ms com AOT Cache. Python fica entre 315 e 638 ms.

Como o teste funciona

k6 (4 vCPU) ──> alvo (2 vCPU / 1 GB) ──> mock-api (4 vCPU / 2 GB, responde em 5 s)
                um alvo por vez: Go, Java JVM, Java Native, Rust ou Python, padrão ou otimizado

Todos os alvos têm o mesmo contrato: GET /health responde 200 ok, e GET /api/io chama a mock-api por HTTP/1.1 e devolve o JSON de 35 bytes que recebeu, ou 502 se a chamada falhar. Os containers ficam na mesma rede do Docker Compose, um alvo de cada vez, com nofile, somaxconn e faixa de portas ampliados em todos. Mock-api e k6 têm o dobro de CPU do alvo e são monitorados: picos acima de 320% de CPU são sinalizados, e saturação invalida a rodada.

O que é medido

  • req/s real: só respostas 200, iniciadas dentro da janela de 180 s. Erros rápidos não inflam o número.
  • Overhead p99: o p99 da latência menos os 5.000 ms da mock-api. É o que o alvo acrescenta.
  • Memória: usage - inactive_file do container, uma amostra por segundo pela API do Docker. O pico é comparado com o limite de 1.024 MiB.
  • CPU-s por 1.000 requisições: CPU consumida na janela dividida pelas respostas 200. É a medida de eficiência que desconta o throughput.
  • Startup: do start do container até o primeiro /health com 200, em 10 execuções, medido de fora e incluindo o custo do Docker.
  • OOM: kill quando o kernel encerra o processo; heap quando o log tem OutOfMemoryError e o container continua de pé.

Dois modos de carga: VUs e 100 req/s

Na carga por VUs (MODE=vus, executor constant-vus do k6), cada usuário virtual chama /api/io, espera a resposta e chama de novo, sem pausa. Como a mock-api leva 5 s, o throughput ideal é o número de VUs dividido por 5: 1.000 VUs dão 200 req/s, 5.000 dão 1.000 e 10.000 dão 2.000, e o alvo sempre tem tantas chamadas paradas quanto VUs. É um modelo fechado: quando o alvo atrasa, cada VU demora mais para repetir e o throughput cai sozinho. Foi o que aconteceu com o Native com 5.000 VUs na trilha padrão, que fez 866,6 req/s com 0 erros. Pausas de GC levaram a latência mediana para 5,67 s, e 5.000 / 5,67 s dá cerca de 880 req/s. Por isso a lentidão aparece aqui como req/s abaixo do ideal, e não como fila. Cada VU começa com um atraso aleatório de até 5 s, para as chamadas não chegarem em ondas.

Na carga por taxa (MODE=rate, executor constant-arrival-rate), o k6 inicia exatamente 100 requisições por segundo, responda o alvo rápido ou devagar. É um modelo aberto, como o tráfego que chega de fora num serviço real: se o alvo ficar lento, as chamadas se acumulam em vez de diminuir. Com 100 req/s e 5 s de espera, ficam cerca de 500 chamadas em andamento (100 × 5), metade das 1.000 do menor nível por VUs. O k6 pré-aloca 600 VUs (6 vezes a taxa) e pode chegar a 4.000 (40 vezes). Se precisasse de mais, a iteração seria descartada e contada em dropped_iterations. Nas 30 rodadas, nenhuma foi descartada.

A rodada de 100 req/s não mede capacidade, porque todos os alvos sobram. Ela mostra o custo em carga leve e estável: quanta memória e CPU cada plataforma consome para atender a mesma demanda moderada, e se as otimizações feitas para 10.000 VUs pioram algo quando a carga é baixa. Nesse modo, o req/s ideal é a própria taxa. A janela, o warm-up e as 3 repetições são os mesmos da carga por VUs, e o startup não é medido de novo, porque não depende do modo de carga.

Comandos das duas cargas
# Carga por VUs (padrão): 1.000, 5.000 e 10.000 VUs, 3 repetições
TARGETS="go-fiber java-jvm java-native rust-axum" scripts/run-all.sh

# Carga constante de 100 req/s nos 10 alvos, sem medir startup
MODE=rate LEVELS=100 STARTUP_RUNS=0 \
TARGETS="go-fiber java-jvm java-native rust-axum go-fiber-opt java-jvm-opt java-jvm-zgc java-native-opt java-native-g1 rust-axum-opt" \

Java: do Tomcat ao Jetty

Com Tomcat, a JVM esgotava 1 GB com 10.000 VUs. Para saber onde a memória ia, o alvo padrão rodou com 4 GB e teve o heap inspecionado com jmap -histo. Com 10.000 conexões, havia 329 MB em 40.247 arrays char[], cerca de 32,9 KB por conexão, e 758 MB em byte[], além de cerca de 300 mil objetos ByteChunk, CharChunk e MessageBytes do Tomcat. A geração old do G1 ocupava cerca de 1.330 MiB, mais que o heap inteiro disponível em 1 GB (768 MiB). Não há propriedade do Tomcat que reduza esses char[] por conexão, então o servidor foi trocado.

A troca para o Jetty não funcionou de primeira: com os padrões, ele travou num limite de concorrência e, depois, o cache de cabeçalhos ocupou quase 1 GB sozinho. A sequência abaixo mostra cada etapa, com 10.000 VUs e 60 s medidos, uma repetição.

O código

opt/java-spring/src/main/java/bench/JettyConfig.java
@Configuration
public class JettyConfig {

    // O VirtualThreadPool limita a 200 tarefas simultâneas por padrão: só 40 req/s com 5s de espera.
    private static final int MAX_CONCURRENT = 20000;

    @Bean
    @Order(Ordered.LOWEST_PRECEDENCE)
    WebServerFactoryCustomizer<JettyServletWebServerFactory> jettyLimits() {
        return factory -> {
            factory.setThreadPool(new VirtualThreadPool(MAX_CONCURRENT));
            // Cada conexão mantém o próprio cache de cabeçalhos, cerca de 100 KB por conexão.
            factory.addServerCustomizers(server -> {
                for (var connector : server.getConnectors()) {
                    var http = connector.getConnectionFactory(HttpConnectionFactory.class);
                    if (http != null) {
                        http.getHttpConfiguration().setHeaderCacheSize(0);
                    }
                }
            });
        };
    }
}

O customizador roda com a menor precedência para ser aplicado depois da configuração automática do Spring Boot, que também define o pool quando spring.threads.virtual.enabled=true. O cache de cabeçalhos é desligado nos conectores já criados, por isso o ajuste usa addServerCustomizers.

O que estes ajustes custam

  • Cabeçalhos: o limite de 2 KiB serve para este teste, mas pode rejeitar requisições reais com cookies ou tokens grandes. O mesmo vale para o Go otimizado.
  • Cache de cabeçalhos: desligá-lo pode custar CPU na leitura dos cabeçalhos de cada requisição. Esse efeito não foi medido isoladamente.
  • Concorrência quase sem limite: com VirtualThreadPool(20000), o servidor aceita até 20.000 tarefas simultâneas. Se um limite for necessário em produção, ele precisa vir de outro lugar, como um limitador de requisições.
  • Respostas maiores: o teste devolve 35 bytes. Buffers de 2 KiB podem custar mais com corpos grandes.
  • Comparabilidade: o Java otimizado não é a mesma aplicação com outras flags, porque o servidor HTTP mudou. O Native com G1 também muda de distribuição.

Limites destas conclusões

  • O cenário é só espera de I/O: sem trabalho de CPU no handler, TLS, serialização relevante ou banco. Em Python, CPU real disputaria o mesmo event loop.
  • Os resultados valem para 2 vCPU e 1 GB. O fracasso do Java padrão com 10.000 VUs não mostra que ele não aguente essa carga com mais memória.
  • A memória da JVM não é o mínimo necessário. O coletor ocupa o heap disponível antes de coletar, e o mesmo vale para o Native com G1.
  • Comparações entre rodadas são indiretas. Go, Rust, Java e Python foram medidos em rodadas diferentes na mesma máquina. O Go repetido como controle variou muito pouco, mas diferenças pequenas não devem ser lidas como efeito.
  • Os ajustes otimizados foram feitos para este teste e não valem automaticamente para produção.
  • Os tempos autodeclarados de Go, Rust e Python não são comparáveis. Use o tempo até ficar pronto.
